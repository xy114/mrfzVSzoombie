## 6. 结论与建议

### 核心发现

经过搭建 Three.js 原型验证，3D 化的技术路线是**可行**的（Three.js WebGL + 正交摄像机 + 卡通渲染），但真正的瓶颈不在技术，而在**资产生产成本**。

- **渲染技术**：Three.js MeshToonMaterial + 反 hull 描边在 2.5D 俯视视角下可以产出可接受的卡通效果，性能不是问题（简单几何体轻松 60fps）
- **程序化占位模型**：用 Three.js 几何体拼合的占位模型，精细度远不及原项目的 2D GIF 手绘资源。即使经过优化（ExtrudeGeometry 花瓣、多层结构），依然无法达到手绘美术水平
- **真实 3D 模型**：要达到与原项目 GIF 相当的美术质量，需要为每个植物/僵尸角色单独建模（Blender 建模 + 贴图 + 骨骼绑定），当前项目已有 9 种植物 + 7 种僵尸，总计 16+ 个角色需要建模，工作量和成本远超预期

### 是否建议推进 3D 化？

**不建议在当前阶段全面推进。** 原因：

1. 原项目的 2D GIF 资源已经具备较高的美术完成度，3D 程序化几何体无法超越
2. 要达到同等或更高美术水平，需要专业 3D 建模投入，成本远高于收益
3. 游戏核心玩法不依赖第三维度（固定俯视 2.5D 视角），3D 带来的玩法增益为零
4. 当前阶段更适合将资源投入到玩法深度、更多角色、关卡内容等方面

### 后续可选方向

如果未来条件成熟（有 3D 建模资源），可参考本原型的技术方案（Three.js + 正交摄像机 + 卡通渲染管线）快速集成。本 `3d/` 文件夹保留作为技术参考。原型中已包含：

- Three.js 项目脚手架（importmap + ES Modules）
- 正交摄像机 + 场景系统
- 卡通渲染管线（MeshToonMaterial + 反 hull 描边 + 阴影）
- GLTFLoader 模型加载基础设施
- 格子坐标 → 世界坐标转换
- 完整的技术文档（本报告 + README）
